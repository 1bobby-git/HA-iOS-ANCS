# iOS ANCS companion 0.6.13 / Firmware 0.3.9

## Changes and compatibility

Wi-Fi recovery remains active after the 45-second setup-AP threshold. One existing runtime task owns STA connection attempts; failed attempts use 5/15/30/60-second waits with bounded jitter. Each attempt has a 20-second IP deadline. Repeated explicit authentication errors use a 300-second wait; saving corrected credentials immediately starts a new profile generation. Recovery AP and manual setup intent remain distinct. Credentials and BLE bonds are not automatically erased.

BLE diagnostics separate the saved-peer query from the current link, authentication, encryption, service discovery and both CCCD subscriptions. `bonded` retains its legacy meaning. Authentication has a 30-second deadline, discovery 15 seconds, each subscription 10 seconds, with two bounded in-session retries and a 90-second overall preparation limit. A saved peer continues to reconnect without opening an unrestricted enrollment window. Explicit enrollment can clear the no-peer authentication protection without rebooting; Replace enrollment remains a separately confirmed, destructive operation.

MQTT reconnect is resumed after IP recovery, and retained availability/state are refreshed. Previous MQTT and authentication error codes/times remain diagnostic history; no password, BLE key or notification text is included in the new diagnostics. PUBACK confirms broker acknowledgement, not Home Assistant processing. Existing queue capacity, TTL, QoS and relay-ID deduplication are unchanged.

HA retains existing device and entity identifiers and adds only connection-state and notification-ready diagnostic entities. Missing older-firmware fields are unknown rather than false. Status expires after 180 seconds; restored retained state is not immediately considered live. Source-entity mode requires advancing device uptime for new-schema status. Retained notifications seed history without firing a new notification event. Last-notification history is preserved independently of connection readiness.

## Build and verification

The release contains seven target factory images and separate application images. `release-builds-v0.3.9.json` maps the full source commit to each factory SHA-256, application SHA-256, embedded ELF SHA-256 and partition-table SHA-256. The packaging check compares the embedded application descriptor's ELF fingerprint, not unrelated factory/app hashes.

Existing project commands:

```sh
python -m pip install -r requirements_test.txt
python -m pytest -q tools/tests tests
python -m compileall -q custom_components/ha_ios_ancs
# In the repository's ESP-IDF 6.0.2 environment:
TARGET=esp32c6 bash tools/build.sh
python tools/package_firmware.py --target esp32c6 --build-dir build-esp32c6 --output artifacts/esp32c6
```

Clock-controlled host tests exercise long Wi-Fi outages, retries, cancellation, duplicate events, authentication backoff, registration expiry and the actual authentication-guard helper. HA tests cover missing fields, retained notifications, stale expiry generations, advancing/stalled/reset uptime, entity identifiers and subscription cleanup. The build matrix checks ESP32, C2, C3, C5, C6, C61 and S3 using ESP-IDF 6.0.2.

## Installation and rollback safety

**HACS updates the companion integration only. It does not update the ESP32 firmware.** Reload/restart of the user's HA instance and physical ESP32 update are separate operations.

The browser installer uses a merged factory image beginning at offset 0. It is a **new-installation** path: even without full erase, image padding can overwrite the BLE NVS region. Do not use it to promise pairing preservation.

For an existing device, first confirm the exact chip, flash size and current partition layout against the release metadata. The unchanged repository layout has `nvs` at `0x9000`, the application at `0x10000`, and `provision` at `0x210000`. An application-only update must write only the verified `.app.bin` to the application offset recorded in that target's build metadata; it must not erase the chip, rewrite the partition table or write the factory image. This project currently uses a single factory app partition, so this is not an A/B OTA rollback claim. Serial connection/reset and flash require explicit physical-device approval.

Keep the previous application image and matching partition fingerprint for rollback. If the current device's layout or encryption/security configuration cannot be verified, stop rather than guessing an offset. Firmware rollback cannot restore a pairing explicitly removed from an iPhone or board. NVS/full-flash backups contain credentials and keys and must remain encrypted/private, never in repository files or public CI artifacts.

## Hardware acceptance still required

No USB device was flashed, rebooted or erased during this implementation. No network or BLE outage was injected on the user's devices. Compilation and host/HA unit tests do not prove iPhone interoperability, bond-write persistence or long-term stability. The original `bonded=false` cause remains unknown; a successful cached bond query is not proof of an NVS write commit.

Record a normal encrypted link, both subscriptions, a new privacy-safe test notification, MQTT accepted/PUBACK deltas, and reception on the intended HA device before injecting each separately approved fault. Test AP absence for 60 seconds and 5 minutes, AP absence at boot, MQTT-only outages, BLE range/Bluetooth toggling, incorrect PIN then retry, enrollment expiry/protection, one-sided pairing mismatch, discovery/subscription failure, reboot, USB power reconnection, application update, simultaneous outages and old/removed/duplicate events.

With valid credentials and working DHCP/DNS/broker, the proposed AP-restoration acceptance limit is Wi-Fi plus MQTT within 120 seconds, including a remaining failed attempt (20), maximum retry wait/jitter (65), fresh IP attempt (20), MQTT connection (10) and scheduling margin (5). HA state should follow within another 10 seconds. iPhone initiation timing is separately measured, not guaranteed by advertising alone. Stop on unexpected peer loss, storage errors, repeated reboots, duplicate automation events, credential leakage or missed recovery limits. Restore the environment first; never use automatic erase or repeated reboot as recovery. Run separate 24-hour and 72-hour observations before claiming endurance results.
